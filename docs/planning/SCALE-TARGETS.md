# Shark-MQTT 大规模目标分层与 EMQX 对标基线

- **文档类型**：规划基线（Planning Baseline）
- **作者**：产品经理 许清楚（Xu）
- **日期**：2026-09-10
- **关联项目**：Shark-MQTT（本地 `G:\shark-mqtt`，`github.com/X1aSheng/shark-mqtt`）
- **对应用户问题**：*"Shark-MQTT 能否集群部署，达到大规模目标？"*
- **本文目的**：把模糊的"大规模"量化为 4 个可评审层级，并给出 EMQX 对标数据，作为后续架构评审的**统一标尺**。

---

## 0. 结论速览

1. **"大规模"必须分层，不能用一句话回答。** 本文把规模拆为 **L1 小型 / L2 中型 / L3 大型 / L4 超大**，每层给出并发连接、吞吐、节点数、P99 延迟、SLA、硬件量级 6 个维度的硬门槛。
2. **Shark-MQTT 当前处于 L1（小型）**：定位依据是**默认配置下的单机形态**——`max_connections` 是**可调配置项**（默认 10,000，见 `config/config.go:35,93`；可经 `broker/options.go:163` 的 `WithMaxConnections(n)` 编程设置，`0` 表示不限），**不是架构硬上限**；真正的单机天花板在资源侧（内存 / 文件描述符 / CPU / GC），不在这个配置值上。但"可配置 ≠ 已验证"：**> 1 万连接的稳定性未经验证**。实测单机吞吐约 1.8 万 msg/s，低于 L1 的 5 万 msg/s 门槛上限；且**无任何集群/冗余能力**，可用性维度实际达不到 L1 的 99.5% SLA 要求。
3. **跨入 L3/L4 是"品类跃迁"，不是"加个配置"**：需要集群成员管理、跨节点路由、会话路由、故障转移、集群级监控等一整套分布式能力（详见第 5 节）。当前集群相关代码为 **0 文件**。
4. **EMQX 的层级上限**：官方宣称单集群 1 亿连接 / 500 万+ msg/s / 100 节点（企业版）；官方 2022 年自测报告在 23 节点集群上达成 1 亿连接 + 100 万 msg/s。**注意：这些均为 EMQX 官方自测（官方宣称），非第三方独立复现。**

## 1. 规模分层表

> 口径说明：
> - **并发连接数** = 同时在线 MQTT 会话数（TCP/TLS/WS 连接）。
> - **消息吞吐** = 集群**入站发布**的持续聚合速率（msg/s），非峰值突发。
> - **P99 延迟** = 负载下 publish→subscribe 端到端 P99。
> - **SLA** = 月度可用性目标（需冗余/故障转移才可能达成）。
> - **硬件量级** = 承载该层的**单节点**典型配置；L3/L4 需多节点叠加。

| 层级 | 并发连接数 | 消息吞吐（msg/s） | 集群节点数 | P99 延迟 | 可用性目标（SLA） | 典型硬件量级（单节点） |
|---|---|---|---|---|---|---|
| **L1 小型**<br>Small | ≤ 10,000 | ≤ 50,000 | 1（单节点） | ≤ 50 ms | 99.5%（单点可接受，允许短时中断） | 2–4 vCPU / 4–8 GB（VM / 边缘盒子 / 嵌入式） |
| **L2 中型**<br>Medium | 1 万 – 10 万 | 5 万 – 50 万 | 1（高配单机）或 2–3 节点 | ≤ 20 ms | 99.9%（≤ 43 min/月中断） | 8–16 vCPU / 16–32 GB |
| **L3 大型**<br>Large | 10 万 – 100 万 | 50 万 – 500 万 | 3 – 10 节点 | ≤ 10 ms | 99.95%（≤ 22 min/月中断） | 16–32 vCPU / 64–128 GB 每节点 |
| **L4 超大**<br>Hyperscale | > 100 万 | > 500 万 | 10 – 100+ 节点（可多集群/全局互联） | ≤ 5 ms | 99.99%（≤ 4.3 min/月中断） | 32–64 vCPU / 128–256 GB 每节点 |

**层级间的关键分水岭（评审关注点）**

| 跨越 | 触发的结构性要求 |
|---|---|
| L1 → L2 | 单节点垂直扩容 + 资源调优（文件描述符、内核网络栈、连接内存占用）；尚不需要集群 |
| L2 → L3 | **必须引入集群**：单节点已达内存/文件描述符/CPU 上限，只能水平扩展；需要跨节点路由 + 负载均衡接入 |
| L3 → L4 | 集群规模化管理：多集群/区域互联、自动扩缩、集群级一致性、全局限流与监控聚合 |

## 2. 场景映射

| 层级 | 典型业务场景 | 说明 |
|---|---|---|
| **L1 小型** | 边缘网关、单个车间/产线、中小 IoT 平台起步、开发测试环境、嵌入式宿主程序 | 设备量 10³–10⁴；常要求**单二进制 / 零依赖 / 可嵌入**，与 Shark-MQTT 定位高度契合 |
| **L2 中型** | 中型 IoT SaaS、楼宇/园区管理、连锁零售门店、区域能源计量 | 设备量 10⁴–10⁵；开始要求高可用与运维接口（API/Dashboard） |
| **L3 大型** | 车联网（IoV）、智慧城市、工业 IIoT（工业园区）、省级电力/水务 | 设备量 10⁵–10⁶；必须集群 + 水平扩展 + 故障转移；消息需出站到数据平台 |
| **L4 超大** | 全国级车联网/运营商级 IoT、国家级智慧城市、跨区域全球业务平台 | 设备量 10⁶–10⁸；需多集群/全局命名空间互联、跨区域容灾、99.99% SLA |

## 4. Shark-MQTT 当前位置

**结论：L1（小型）入门——默认配置下性能量级落在 L1 区间，但可用性维度不达标，且大连接数未经验证。**

| 维度 | Shark-MQTT 现状 | 对照门槛 | 判定 |
|---|---|---|---|
| 并发连接 | `max_connections` **可配置**，默认 10000（`config/config.go:35,93`）；可编程设置、`0` = 不限（`broker/options.go:163`、`api/api.go:114`）；仅当 `> 0` 时生效（`broker/server.go:242`、`broker/broker.go:168`） | L1 门槛 = 10,000 | ⚠️ **默认值落在 L1 区间，但该值可调、并非架构上限**；真实约束在资源侧（内存 / 文件描述符 / CPU / GC）——**> 1 万连接未经验证**（缺长跑稳定性与负载下 P99 数据） |
| 消息吞吐 | 实测约 **1.8 万 msg/s** 入站（探针：60K 条 / 3.34 s，10% QoS1，峰值约 5 核）；单流 E2E QoS0 68 µs | L1 上限 = 5 万 msg/s | ✅ 落在 L1 区间内（有头部余量，但未验证到 5 万） |
| 集群节点数 | **0 个集群文件**（cluster/bridge/rule 关键词检索命中 0） | L1 = 单节点 | ✅ 符合 L1（但无法进入 L2+） |
| P99 延迟 | 未做负载下 P99 端到端测量；仅有单流延迟基准 | L1 = ≤50 ms | ❓ **未获取到 P99 实测数据**（需补测） |
| 可用性 SLA | 无冗余、无故障转移、无 HA；单进程重启即中断 | L1 = 99.5% | ❌ **不达标**（单点故障无法保证 99.5%） |
| 硬件量级 | 实测环境：AMD Ryzen 7 8845HS / Windows 11；~30 KB/连接稳态、~55 KB/连接峰值；1,000 连接建立 378 ms（≈2,645 conn/s） | L1 = 2–4 vCPU / 4–8 GB | ✅ 匹配 L1 |

**判定依据小结**
- **性能侧**：处于 L1 区间（默认 1 万连接 + 约 1.8 万 msg/s）。注意：默认连接数是**可调配置而非能力上限**，当前真正缺的是 **> 1 万连接的长跑稳定性数据与负载下 P99 数据**——"可配置 ≠ 已验证"，这才是 L1 定位的诚实依据。
- **架构侧**：严格单节点，`deploy/k8s/` 下虽有 Deployment/HPA/Helm，但**多副本之间互不通信**，不构成集群，HPA 扩容只会得到多个独立实例（存在误导部署者的隐患）。
- **可用性侧**：无任何冗余，实际可用性低于 L1 的 99.5% 要求，属于"性能达 L1、可靠性未达 L1"。

> 一句话：**Shark-MQTT 今天是一个优秀的 L1 单机 Broker；能否"达到大规模"，等价于"能否从 L1 跨到 L3/L4"——这是一个需要新增整个分布式子系统的问题。`max_connections` 可以调大，但那只是单机资源上限的一个开关，并不构成集群能力：L2→L3 的结构性门槛（跨节点路由、会话路由、故障转移）与这个配置值无关。**

> **单机容量边界另见**：本文只界定"是否达 L1/L2/L3"，不测算单节点在无集群前提下能垂直扩容到多大。单机容量的量化测算与调优清单（内存 / 文件描述符 / CPU / GC 上限）由架构师在 `docs/architecture/CLUSTER-FEASIBILITY.md` 的单机容量测算章节给出，建议一并评审。

## 5. 「达成大规模」硬性能力清单（给架构师的输入）

### 5.1 集群能力（跨入 L3/L4 的必要条件，P0）

| # | 能力 | 说明 | 缺失现状 |
|---|---|---|---|
| C1 | **集群成员管理与节点发现** | 支持 static / DNS / etcd / K8s Service 等发现；成员上下线感知与集群视图 | ❌ 完全缺失 |
| C2 | **跨节点消息路由** | 维护"主题过滤 → 节点集合"路由表；订阅/退订在集群内传播；发布时仅投递到持有订阅的节点 | ❌ 完全缺失 |
| C3 | **会话路由（粘性路由或迁移）** | 会话归属某节点（sticky）或支持会话迁移；离线消息必须路由到会话当前所在节点 | ❌ 完全缺失 |
| C4 | **共享订阅的集群级路由** | 跨节点 round-robin / random / sticky / hash（当前仅**单进程内** round-robin） | ❌ 缺失 |
| C5 | **故障转移与重平衡** | 节点宕机时其连接重连、订阅重建、retained/will 语义保持；新节点加入后重平衡 | ❌ 完全缺失 |
| C6 | **分布式状态存储** | 分布式会话表 / 订阅表 / retained 存储；一致性模型（强一致 vs 最终一致）需明确设计 | ❌ 缺失（redis/badger 仅单实例语义，且存在全表 SCAN 风险 S1/S3） |
| C7 | **集群级可观测性与监控聚合** | 跨节点指标聚合、集群概览 API、节点健康与告警 | ❌ 缺失（仅有单进程 Prometheus 指标） |
| C8 | **分布式限流与配额** | 全局速率限制 / 每客户端配额在集群维度的一致性语义 | ❌ 缺失（仅单节点 `rate_limit.go`） |
| C9 | **负载均衡接入与真实 IP** | LB / K8s Ingress 后接入；Proxy Protocol 解析真实客户端 IP；多监听器 | ❌ 缺失（单 listener 结构） |
| C10 | **集群运维能力** | 滚动升级、节点迁移/重平衡不停机、配置热重载、集群级备份恢复 | ❌ 缺失（配置仅启动时读取，无 reload） |

### 5.2 单节点在大规模下也需补齐的能力（P0/P1）

| # | 能力 | 为什么在大规模下是硬需求 |
|---|---|---|
| S1 | **HTTP 管理 API**（客户端列表/踢下线/会话/订阅/retained/发布） | 10 万+ 连接时无法靠日志运维；也是集群管理的载体 |
| S2 | **配置热重载** | 大规模下调一个限流阈值不应重启进程 |
| S3 | **多监听器（listener 数组）** | 大规模场景常需明文/TLS/WS/不同端口并存 |
| S4 | **连接容量调优与内存控制** | 大规模天然触及文件描述符 / conntrack / 连接内存上限；需内核调优指引 + 连接内存优化（当前 ~55 KB/连接峰值） |
| S5 | **存储后端的批量与原子操作**（S2/S3/S4 遗留风险） | redis/badger 的 SCAN 全表扫描与逐条操作会在会话量增大时线性劣化 |
| S6 | **P99 负载延迟实测与 SLO 基线** | 当前无负载下 P99 数据，无法进入 L2 的延迟承诺 |

### 5.3 分层准入清单（可作评审 Checklist）

| 目标层级 | 必须补齐的能力 |
|---|---|
| **L2 中型** | S1 S2 S3 S4 + P99 实测；单节点垂直扩容验证（通过调高 `max_connections` 并配套内核/资源调优，把当前**未验证区间**——> 1 万连接与吞吐余量——验证到 10 万连接 / 50 万 msg/s 量级） |
| **L3 大型** | L2 全部 + **C1–C10**（集群最小可用：发现 + 路由 + 会话路由 + 跨节点共享订阅 + 故障转移 + 集群监控） |
| **L4 超大** | L3 全部 + 多集群/区域互联（全局命名空间）、自动扩缩、跨区域容灾、全局一致性与全局限流 |

## 6. 待澄清问题（Open Questions）

| # | 问题 | 影响 |
|---|---|---|
| Q1 | "大规模"的目标层级是 **L3** 还是 **L4**？还是仅需 L2？ | 直接决定所需工作量（L3 已需完整集群子系统，L4 再叠加多集群互联） |
| Q2 | 目标场景是**云平台**还是**边缘/嵌入式**？ | 决定是否值得投入分布式子系统，或聚焦单机垂直扩展 |
| Q3 | 是否接受"**粘性路由（无会话迁移）**"作为集群第一版？ | 可显著降低首版复杂度，但节点故障时持久会话体验受影响 |
| Q4 | 分布式状态的一致性模型要求（强一致 / 最终一致）？ | 决定存储选型与脑裂处理策略 |
| Q5 | 集群规模上限目标（3–7 节点 / ≤100 节点）？ | 决定拓扑（全网状 vs core/replicant 读写分离） |
| Q6 | 是否需要 **MQTT Bridge / 集群连接（Cluster Linking）**？ | 影响跨集群/区域互联的能力设计 |
| Q7 | Shark-MQTT 的差异化定位（零依赖/可嵌入/MIT）是否必须在集群化后保持？ | 若必须保持，集群方案不能强依赖外部中间件（etcd/外部 DB） |
