# 四个 MQTT Broker 对比与 shark-mqtt 性能补齐

> 日期: 2026-10-17 12:15 (UTC+8)
> shark-mqtt 基线: `81d95f344`
> 对比对象: smart-mqtt (Java), smart-mqtt-4g (Go), mica-mqtt (Java)
> 目的: 用可核对的数据定位 shark-mqtt 的位置, 并标出还缺哪些测量

---

## 1. 先说结论

| 结论 | 依据 |
|------|------|
| shark-mqtt 的**协议完整性**在四者中最好 | 仅 shark-mqtt 处理 AUTH(0x0F) 全流程; 属性合法性与固定头 flags 双向校验为独有 |
| shark-mqtt 的**体积**比 Java 方案大一个量级, 但比"Java + JRE"小两个量级 | 11.7 MB Go 静态二进制, 含运行时; smart-mqtt 的 <800 KB 是不含 JRE 的 jar |
| shark-mqtt 的**吞吐数据是四者里最不完整的** | 只测过 4 订阅者小 fanout, 没测过高连接数与高 fanout; 另两家有公开的 35 万 - 90 万 msg/s 数字 |
| 现有数字**不能直接横向比** | fanout 倍数、硬件、平台、是否含客户端开销全部不同; 第 4 节给出归一化口径 |
| mica-mqtt 与 shark-mqtt **不是同类** | 前者是嵌入式组件 (client + server 库), 后者是完整 broker 二进制 |
| **单机每核约 18 万投递/s; 两核独占可达 44.9 万 msg/s** | 4.2b 与 4.7 节: broker 独占时 QoS 0 P50 182 us, fanout 200 时 P50 3.85 ms; 同机竞争会低估 40% |
| **"79k 投递/s" 是 rate 参数的回声, 不是能力上限** | 4.9 节: 同样 2 核, 1 KB payload 在 rate 100k 时达到 353k 投递/s, CPU 仅 1.37/2 核, 瓶颈是 2.9 Gbps 链路带宽 |
| **空闲连接成本 35-38 KB/连接, 线程数不随连接数增长** | 4.6 节实测: 1,000 连接 51.4 MB, 4,500 连接 173.9 MB, 线程始终 19-21 |
| **已验证 8,000 空闲连接, 每连接约 31 KB** | 4.6 节: Python 裸 socket 在阿里云 2C4G 上完成 8,000 次 CONNECT/CONNACK, 零错误; loadgen 的 5,000 上限是客户端问题, 非 broker |

## 3. 协议完整性对比

这一项 shark-mqtt 领先, 且有可指认的代码依据:

| 能力 | shark-mqtt | smart-mqtt | 说明 |
|------|-----------|-----------|------|
| AUTH (0x0F) 报文 | 完整 (握手期 + 会话内重认证) | **完全不处理** | smart-mqtt `MqttHeaderDecoder` 的 switch 无 case 15, 收到 AUTH 直接抛异常 |
| 出站 PUBLISH 属性中继 | 逐属性转发, Topic Alias 剥离 | **每条出站 PUBLISH 构造空 PublishProperties** | 导致 MQTT 5.0 Section 4.10 的请求/响应模式在 smart-mqtt 上不可用 |
| 属性归属校验 (Table 2-4) | 编解码双向, 11 个 locus + 27 条 probe | 未做 | 非法属性 ID 与重复属性分别判 Malformed / Protocol Error |
| 固定头 flags 校验 | 编解码双向 | 部分 | shark 对 PUBREL/SUBSCRIBE/UNSUBSCRIBE 的 0b0010 组有专门处理 |
| 出站 Maximum Packet Size 约束 | 编码层收口 | 未见 | 超限报文按规范丢弃而非截断 |
| 解码流对齐 | 拒绝的报文只消费自己的 Remaining Length | 未见 | 防止用对端可控长度索赔 64 KiB |

> 注: smart-mqtt 的两项判定来自其 Java 源码 (`enums/MqttMessageType.java:18`, `MqttHeaderDecoder` switch), 记录在 `docs/reports/SMART-MQTT-GAP-ANALYSIS-261014-2125.md`。

## 4. 性能数据

### 4.1 shark-mqtt 实测 (本轮)

**环境**: Windows 11, AMD Ryzen 7 8845HS (8C16T), Go 1.26.1, broker 与 loadgen 同机竞争 CPU。
**方法**: `tools/loadgen` 通过项目自身 client 包驱动, 延迟由载荷内时间戳在订阅端计算 (端到端, 含编解码与写队列)。

| 场景 | 目标 | 实际发送 | 投递 | frout | P50 | P99 | P999 |
|------|------|---------|------|-------|-----|-----|------|
| QoS 0, 4 sub / 8 pub, 256 B | 20,000 msg/s | 19,968 msg/s | 79,873 msg/s | 400% | 0.0 us | 1,048 us | 1,823 us |
| QoS 1, 4 sub / 8 pub, 256 B | 10,000 msg/s | 9,994 msg/s | 39,975 msg/s | 400% | 0.0 us | 598 us | 1,212 us |

**资源**: 空载工作集 14.5 MB / 9 线程; 两轮压测后工作集 23.1 MB, 峰值 24.4 MB。

### 4.4 为什么不能直接比

| 差异 | shark-mqtt | smart-mqtt-4g | 影响 |
|------|-----------|--------------|------|
| fanout 倍数 | 4 | 2000 | 投递数是 fanout 的倍数, 900k 除以 2000 只有 454 主题发布/s |
| 发布者数 | 8 | 10-2000 | 并发连接数不同 |
| 是否含客户端开销 | 含 (项目自身 client) | 未声明 | 若用外部压测器, broker 侧数字会更好看 |
| 硬件 | 8C16T 笔记本 CPU | i9-12900HK (14C20T) | 核数差 ~1.7 倍 |
| CPU 占用是否公布 | 是 | 否 | 无法归一化 |

**换算尝试** (仅作量级参考, 不可作为结论): 若把 4g 的 M2 数字按 fanout 归一, 主题发布率约 454/s; shark 在同口径 (4 sub) 下是 79,873 / 4 = **19,968 主题发布/s**。这个对比反而显示 shark 在小 fanout 下更强, 但两者的订阅者规模相差 500 倍, 场景完全不同, 因此**不能据此下结论**。

真正缺的是: **shark-mqtt 没有在高 fanout (数百至数千订阅者) 与大连接数 (万级) 下测过**。这是本节最重要的发现。

### 4.5 fanout 拐点 (本轮补充测量)

先测 500 订阅者时看到一个比"峰值吞吐"更有用的现象: 投递量上去了, 延迟崩了。于是按 fanout 梯度补测, 全部为 QoS 0 / 1 发布者 / 256 B / Windows 同机:

| fanout | 发布者 | 目标 rate | 实际发送 | 达成率 | 投递/s | P50 | P99 |
|--------|-------|----------|---------|-------|---------|-----|-----|
| 100 | 1 | 2,000 msg/s | 1,984 | 99% | 198,379 | 0 us | 4,390 us |
| 200 | 1 | 2,000 msg/s | 1,433 | 72% | 280,276 | 602,004 us | 914,162 us |
| 200 | 8 | 2,000 msg/s | 1,715 | 86% | 313,695 | 1,675,985 us | 5,001,222 us |
| 500 | 1 | 2,000 msg/s | 590 | 30% | 290,286 | 1,383,172 us | 2,519,888 us |
| 500 | 8 | 2,000 msg/s | 823 | 41% | 298,100 | 6,573,109 us | 12,435,333 us |

**读法**:

- **实时上限在 fanout 100 与 200 之间**。100 订阅者时发布速率达成 99%、P99 4.4 ms, 属于实时; 200 订阅者时 P50 已经 602 ms, 说明消息在写队列里排队, 系统进入吞吐饱和而非实时投递。
- **吞吐天花板约 290-314k 投递/s, 且与发布者数无关**。这是本轮最有信息量的结果: 把发布者从 1 增到 8, fanout 200 的投递率从 280k 升到 314k (+12%), 而 P50 从 602 ms 恶化到 1,676 ms。吞吐几乎不动、延迟成倍恶化, 说明瓶颈在 broker 的 fanout 投递路径, 不在"单发布连接串行读取"。原本的假设被这组对照否掉了。
- **每逻辑核 30.6k 投递/s** (290,286 / 9.49, 单发布者 500 fanout 那一轮), 按物理核折算约 61k 投递/物理核/s, 高于小 fanout 的 37.1k -- 大 fanout 摊薄了入站解码成本, 与直觉一致。
- **QoS 0 在这里不是"不背压"**。发布端达成率掉到 30%-41%, 是因为 broker 的处理速度反向压住了读取, 不是丢弃策略生效。
- **延迟指标本身要打折看**。P50 6.5 s 意味着队列里积压了数万条, 这是压测器持续施压、broker 始终处理不完的结果, 不是稳态服务延迟。

**这组数字的边界**:

1. 压测端与 broker 同机。500 个订阅连接 + 8 个发布连接本身消耗 CPU, 9.49 逻辑核里含对手方开销, broker 真实占用更低; 反过来, 压测端也可能先撞墙, 所以 300k 是"同机可测到的上限", 不是 broker 的绝对上限。
2. 500 连接在 Windows 回环上, 与 Linux 的 epoll 路径不同, 绝对值不可与 2026-10-15 的 Linux 基线混用。
3. 未测 CPU 的两行 (fanout 100/200 单发布者) 说明它们不是资源饱和点, 但仍受同机竞争影响。

结论 (已由 4.7 节修正): 本节这组数字测的是**同机竞争**下的表现, 天花板约 300k msg/s, 实时边界在 fanout 100-150。把 loadgen 挪到第二台机器、broker 独占两核之后, 同一份二进制达到 **44.9 万投递/s**, 且 fanout 200 时 P50 仅 3.85 ms。

**所以正确的说法是: 单机每核约 18 万投递/s, 实时边界取决于 broker 是否独占 CPU, 而不是 100-150 这个固定数字。** 提高上限仍然只能从每帧 fanout 成本入手 (批量写、合并队列) -- 多发布连接已被证明无效。

### 4.6 空闲连接成本 (idle 模式)

`loadgen` 新增 `-mode idle`: 只做 CONNECT/CONNACK 然后把连接挂住, 不发消息。它回答的是"一万台闲置设备要多少内存", 而不是吞吐。连接走裸 TCP + 项目 codec, 不含 `client.Client` 的开销, 所以量到的是 broker 的每连接成本。

KeepAlive 设为 0, broker 不会主动超时清理, 因此观察的是稳态占用。

| 连接数 | 工作集 | 线程 | 建连速率 | 失败 | 备注 |
|--------|--------|------|---------|------|------|
| 0 (空载) | 14.5 MB | 9 | - | - | - |
| 1,000 | 51.4 MB | 21 | 7,364 conn/s | 0 | 单源 IP |
| 4,500 | 173.9 MB | 19 | 1,171 conn/s | 500 | 压测端 TIME_WAIT 耗尽, 非 broker 拒绝 |
| 5,000 | 未采 | - | 6,200 conn/s | 0 | 重启 broker 后干净环境 |
| 10,000 | 未采 | - | 2,541 conn/s | 5,000 (EOF) | 重启 broker 后干净环境, 恰好一半失败 |

**每连接约 35-38 KB** (51.4-14.5 MB / 1000 = 37.8 KB; 173.9-14.5 / 4500 = 35.4 KB)。两点都落在 35-38 KB 区间, 没有明显的非线性增长。按此外推, 一万台空闲设备约需 370-400 MB 进程内存。

**线程数与连接数几乎无关**: 空载 9, 1,000 连接 21, 4,500 连接 19。Go 的 netpoller 不为每个连接起线程, 这与"每连接一线程"的实现有本质区别, 也是能把万级设备压住的原因。进程句柄数与连接数同阶 (5,000 连接时 Handles=5290)。

### 10000 连接只成功一半 -- 定位结果: 是压测端, 不是 broker

**在阿里云 Ubuntu 26.04 (2C4G) 上复现了完全相同的现象**: 干净 broker、串行建连 (`-idle-parallel 1`)、并发 64, 三种方式都是**恰好 5,000 成功、5,000 失败**, 客户端首次错误 `EOF`。

排查过程与证据:

| 检查项 | 结果 |
|--------|------|
| broker 日志 | 5011 行全部是 `client disconnected`, **没有任何拒绝/超限日志** (`grep -icE 'max|limit|reject'` = 0) |
| 成功的 clientID | 全部是 `idle-0` .. `idle-4999`, 失败的 id >= 5000 完全没出现在服务端 |
| 代码搜索 | `broker/` `config/` `api/` 全仓库无 `5000` 字面量; `max_connections` 默认 10000 |
| 内核参数 | `ip_local_port_range` 28232、`somaxconn` 8192、`tcp_tw_reuse` 2 (loopback 允许重用)、`ulimit -n` 65535, 均正常 |
| `dmesg` | 无 SYN flood 或 listen queue overflow 记录 |

**决定性对照**: 在同一台服务器上用 20 行 Python 裸 socket (不走 loadgen, 但用**同样的 16 源 IP 轮转**策略) 建连并完成 CONNECT/CONNACK:

```
mode=connect ok=8000 err=0 elapsed=0.33s
```

**8,000 个连接全部成功, 零错误。** 同一台机器、同一个 broker、同样的多源 IP 策略。

结论: **broker 能稳定处理 8,000 空闲连接; 5,000 这个上限属于 Go 版 loadgen 客户端。** 待查的是客户端侧 (最可疑的是 `net.IPv4()` 返回的 16 字节 IPv4-mapped 地址用于 `LocalAddr` 绑定时的行为差异), 这属于测试工具问题, 不影响 broker。

对外口径因此修正为: **单机已验证 8,000 空闲连接, 每连接约 31 KB**。

### Linux 上的资源数据 (阿里云 2C4G)

| 连接数 | VmHWM | 线程 | 建连速率 |
|--------|-------|------|---------|
| 0 (空载) | 10.1 MB | 7 | - |
| 5,000 | 161 MB | 9 | 10,508 conn/s |

每连接 (161-10.1) MB / 5000 = **31.6 KB**, 与 Windows 上量到的 35-38 KB 同量级 (Windows 的工作集统计口径本就偏大)。线程数 7 -> 9, 再次确认连接数不换线程。

### 测量方法上踩的坑 (记录下来, 避免重犯)

1. **`| head -N` 会杀死被测程序, 制造假故障。** `go run` 会 fork 子进程, `head` 读满 N 行后关闭管道, 子进程收到 EPIPE 被杀, 其 socket 不正常关闭。表现是下一轮测试里 Established 连接高达 9,801 且逐轮递增, 失败率随轮次单调上升 (281 -> 141 -> 70)。**压测输出只能用 `tail`, 或重定向到文件。**
2. **单源 IP 只能测到 4,500 左右。** Windows 动态端口范围 16,384 个, 客户端主动关闭产生的 TIME_WAIT 会在下一轮把端口吃光。`dialAndConnect` 已改为在 `127.0.0.2` - `127.0.0.17` 上轮转, 端口空间扩大 16 倍。
3. **每轮之间要重启 broker。** 上一轮残留的连接会改变下一轮的结果 (见第 1 点)。
4. **失败率异常时, 先用非 Go 客户端复核。** 本轮最大的弯路是把客户端的 5,000 上限当成了 broker 的缺陷, 直到 Python 裸 socket 在同一台机器上成功 8,000 才定位。压测端出问题时, 换一个实现往往比继续调参数更快。

### 4.7 跨机 fanout 梯度 (broker 独占 2 核)

cloud3 跑 loadgen, cloud2 跑 broker, 私网 0.116 ms, QoS 0 / 256 B / 20 s / 1 发布者:

| fanout | 实际发送 | 投递/s | P50 | P99 | P999 |
|--------|---------|--------|-----|-----|------|
| 200 | 1,885 msg/s | **376,985** | 3.85 ms | 21.5 ms | 35.5 ms |
| 500 | 1,109 msg/s | **448,628** | 2.93 s | 6.96 s | 8.26 s |

**两核机器做到 44.9 万投递/s。** 这直接改写了 4.5 节的结论: 那里测到的 "天花板 290-314k" 与 "实时边界 fanout 100-150", 是 broker 与压测端抢 CPU 时的数字, 不是 broker 的能力。

- fanout 200 时 P50 3.85 ms、P99 21.5 ms, 属于可用范围; 4.5 节同机测得的 fanout 200 已经 P50 602 ms, 差了两个数量级。
- fanout 500 仍然打满: 投递率只比 fanout 200 高 19%, 延迟却从毫秒级掉到秒级。**瓶颈仍在每帧扇出成本, 与 4.5 节的判断一致, 只是真实天花板比原先测到的高。**
- VmHWM 在这轮四组测试后为 49.5 MB (含 500 连接), 线程 9。

测试期间 broker 累计 CPU 111.3 s / 墙钟 100.6 s = 平均 1.11 核 (机器共 2 核)。分段采样只对 QoS 0 那组做了精确归一化, 其余三组只能给区间。

### 4.8 第一次优化尝试: 把 TrackSent 移出会话锁 (收益不显著)

4.7 节的瓶颈指向每帧扇出成本, 于是先做最省事的一处: `Session.TrackSent` 原先对 `s.mu` 取**写锁**, 而它在扇出路径上每条消息每个订阅者都要调一次 -- 一条消息发给 500 个订阅者, 就是同一把写锁上串行 500 次。两个计数器改成原子累加, `Stats()` 在快照里合并。

跨机复测 (同一台 2 核 broker, 同一台压测机, 同样 20 s):

| fanout | 投递/s 改前 | 投递/s 改后 | P50 改前 | P50 改后 | P99 改前 | P99 改后 |
|--------|-----------|-----------|---------|---------|---------|---------|
| 200 | 376,985 | 377,340 (+0.1%) | 3.85 ms | 4.06 ms | 21.5 ms | 27.3 ms |
| 500 | 448,628 | 453,811 (+1.2%) | 2.93 s | 2.66 s (-9%) | 6.96 s | 6.39 s (-8%) |

**结论: 这把锁不是瓶颈。** fanout 500 的吞吐只多 1.2%, 延迟的 8-9% 变化在两次 20 秒运行的噪声范围内; fanout 200 那一组 P99 反而变差, 更说明差异来自抖动而非改进。

改动本身保留 -- 它消除了一个真实的共享写锁, 在订阅者更多的场景 (fanout 数千) 上迟早会显现, 而且代价为零。但**它没有解决 4.7 节观察到的问题**, 这一点必须写清楚, 否则就成了"优化了所以变快了"的错觉。

**下一个嫌疑, 按可能性排序**:

1. **每连接一次 `codec.Encode`**。扇出时同一帧要对每个订阅者各编码一次; 500 个订阅者 = 500 次编码, 其中绝大部分字节完全相同 (只有 QoS、DUP、Subscription Identifier 可能不同)。如果 codec 能把一帧编码到可复用的 buffer, 扇出 500 次可以只编码 1 次再复制 499 次。
2. **每包一次 syscall**。写循环取出多少就写多少, 没有批量合并; TCP 下连续的多个包本可以一次 `write` 出去。
3. **`writePacket` 里的 `b.mu.RLock()` + map 查找**, 每条消息每个订阅者一次全局读锁。可以在进入扇出循环前一次性取锁, 把订阅者的 `clientState` 收集成切片。

这三项都需要改核心路径, 属于有风险的改动, 本轮没有展开。

### 4.9 数据负载测试: payload 梯度与真实饱和点

之前的每一组测试都固定 rate 20,000, 于是"投递 79k"被反复观察成天花板。这组测试把 rate 当成自变量, 才看出那只是目标值乘以订阅者数。

跨机 (broker 独占 2 核), QoS 0, 4 订阅者 / 8 发布者, 每次 20 s。

**固定 rate、改变 payload**: 投递率几乎不动。

| payload | rate | 实际发送 | 投递/s | P50 | P99 |
|---------|------|---------|--------|-----|-----|
| 64 B | 20,000 | 19,808 | 79,230 | 186 us | 523 us |
| 256 B | 20,000 | 19,804 | 79,214 | 174 us | 505 us |
| 1 KB | 20,000 | 19,798 | 79,191 | 188 us | 626 us |
| 4 KB | 20,000 | 19,798 | 79,190 | 216 us | 895 us |

payload 放大 64 倍, 投递率一条直线, 延迟只涨 16%。**每帧的固定开销主导, 字节数不是主要成本** -- 这与 4.5 节"瓶颈是每帧扇出成本"的判断一致。

**固定 1 KB、提高 rate**: 天花板是原来测到的 4.5 倍。

| rate | 实际发送 | 投递/s | 投递率 | P50 | P99 |
|------|---------|--------|-------|-----|-----|
| 20,000 | 19,798 | 79,191 | 400% | 173 us | 505 us |
| 40,000 | 39,248 | 156,993 | 400% | 101 us | 746 us |
| 60,000 | 58,195 | 232,730 | 400% | 190 us | 2,086 us |
| **100,000** | 95,347 | **353,855** | **369%** | 2,644 us | 8,849 us |

rate 从 20k 到 60k 一直是 400% 达成、延迟稳定在百微秒级; 到 100k 才掉到 369%, P50 跳到 2.6 ms。**真实饱和点约 353k 投递/s**, 是此前反复出现的 79k 的 4.5 倍。

饱和时的资源: **CPU 1.37 核 (共 2 核), VmHWM 50.1 MB**。CPU 没打满, 而这一档承载的字节速率是 1 KB x 353,855 = **2.9 Gbps**。**瓶颈在链路带宽, 不在 broker。**

**大包**: 在较低 rate 下同样能跑满。

| payload | rate | 投递/s | P50 | P99 |
|---------|------|--------|-----|-----|
| 4 KB | 5,000 | 20,000 | 156 us | 378 us |
| 16 KB | 2,000 | 7,992 | 258 us | 596 us |
| 64 KB | 500 | 2,000 | 655 us | 1,350 us |

64 KB 单帧投递的 P50 是 655 us, 仍是亚毫秒。全部 400% 达成、零错误。

**这三组数据合起来修正了本报告的一个基础判断**: 此前把 "79k 投递/s" 当成 broker 的能力, 实际那是 rate 参数的回声。正确的说法是: **2 核上, QoS 0 / 4 订阅者的饱和投递率约 353k msg/s, 受限于网络带宽约 2.9 Gbps; 若只看 CPU, 还有约 30% 余量。**

### 4.10 用 profile 定位: 瓶颈是 write(2), 但批量写反而更慢

前几节一直指向"每帧扇出成本", 但那是推断。这一轮先给 broker 加了可选的 pprof 端点 (默认关闭, 见 CONFIGURATION), 再在 200 订阅者负载下采了 30 秒 CPU profile。

**profile 结论 (30 秒, 59 秒样本):**

```
29.84s 50.58%  internal/runtime/syscall/linux.Syscall6
 4.78s  8.10%  runtime.selectgo
 5.38s  9.12%  runtime.mallocgc
 0.41s  0.69%  broker.(*Session).Spec
```

**一半的 CPU 花在 syscall 上, 也就是 `write(2)`。** 编码 (`codec.Encode`) 根本没进前 22 名 -- 之前怀疑的"每订阅者一次编码"被证伪, 它便宜得看不见。`selectgo` 那 8% 是每包一次 channel 收发, `mallocgc` 那 9% 是每包一次对象分配。

**于是做了批量写**: 给 TCP 连接加 16 KB `bufio.Writer`, 写循环一次排空队列 (最多 64 个包) 再 flush, 把每包一次 syscall 摊成每次 flush 一次。WebSocket 保持逐包写入 (每包是一个消息边界)。

**结果相反:**

| 场景 | 投递/s 改前 | 改后 | P50 改前 | 改后 | P99 改前 | 改后 |
|------|-----------|------|---------|------|---------|------|
| fanout 200 | 376,985 | 376,923 | 3.85 ms | **4.89 ms** | 21.5 ms | **31.5 ms** |
| fanout 500 | 448,628 | 438,887 | 2.93 s | **3.76 s** | 6.96 s | 7.73 s |

fanout 200 的 P99 恶化 47%, fanout 500 的吞吐掉了 2%、P50 涨 28%。**改动已回退, 没有进主干。**

**为什么**: syscall 那 50% 主要是**数据拷贝** (用户态 buffer 到内核), 不是调用本身的开销。批量写没有减少要拷贝的字节数, 反而多了一次 buffer 拷贝 (encode -> bufio -> kernel); 同时"连续写 64 个包才 flush"让单个订阅者的处理变成大块串行, 其他连接在等待, 直接体现为尾部延迟变差。

**这条负面结论值得单独记下**: "profile 显示 syscall 占 50%, 所以合并 syscall" 是从热点直接跳到方案的典型误判。热点告诉你在哪花钱, 不告诉你花在什么上; 合并调用次数只有在每次调用有固定开销时才划算。

**下一步该测什么** (profile 已经指明): `mallocgc` 占 9%, 而 fanout 时每条消息要为每个订阅者构造一个 `PublishPacket` 与属性结构。减少这部分分配, 比继续动 syscall 更有希望。

### 4.11 第二次优化尝试: 消除 MatchTopic 的分配 (同样没赢)

4.10 的 profile 里 `mallocgc` 占 9%, 于是先看分配。`-sample_index=alloc_space` 的堆剖析给出了比 CPU profile 更明确的目标:

```
625.07MB 38.11%  broker.addSubscriber (inline)
318.02MB 19.39%  broker.(*Broker).doDeliver
265.51MB 16.19%  strings.genSplit
204.01MB 12.44%  bytes.NewBuffer
```

`-peek` 追下去, `strings.genSplit` 的那 16% **100% 来自 `protocol.MatchTopic`**, 调用者是 `Session.matchSubscriptions` -- 会话级订阅匹配, 每条消息每个订阅都要走一次, 而它每次都 `strings.Split(pattern)` 加 `strings.Split(topic)` 造两个切片。

改成逐级扫描、零分配 (benchmark 验证 `0 B/op, 0 allocs/op, 25.6 ns/op`)。**为了证明语义没变, 用旧实现作为参考实现, 对 22 个模式 x 14 个主题做了对比测试** -- 这一步立刻抓到我第一版的一个真 bug: `$SYS/#` 匹配 `a` 返回了 true, 因为我把"主题耗尽"的分支放在了级别比较之前。

改写后跑实测, 每档 3 次 15 秒:

| | 投递/s (3 次) | P50 (3 次) | P99 (3 次) |
|---|---|---|---|
| 基线 | 377,231 / 377,357 / 376,481 | 4.24 / 4.20 / 4.16 ms | 21.4 / 30.8 / 24.6 ms |
| 零分配版 | 377,020 / 376,858 / 377,069 | **6.17 / 5.64 / 5.81 ms** | 34.5 / 36.5 / 37.6 ms |

吞吐一模一样, **P50 稳定地从 4.2 ms 涨到 5.6-6.2 ms (+35~47%)**。不是噪声: 三次数值各自聚集在各自区间, 而 P99 在两版里都抖得厉害, 所以只看 P50。

**已回退。**

**为什么**: Go 的小对象分配很便宜 (mcache 命中就是几次指针运算), 而"把它换成逐级扫描"要付出更多分支判断。`strings.Split` 是经过专门优化的实现, 在 2-3 级主题上它的固定成本低于一个手写的多分支循环。分配量降了, 延迟反而升了。

**这是本轮第二次同类误判**: 4.10 是"syscall 占 50% 所以合并 syscall", 这里是"分配占 16% 所以消除分配"。两次都是**把 profile 的占比当成了可优化的因果**: profile 说这块花了多少资源, 没说这块花得冤枉。

**真正该看的指标**: 分配只影响 GC 频率, 而 GC 只有在占 CPU 显著比例时才值得动。这台机器上 GC 并不在 CPU profile 的前几名 -- 也就是说 16% 的分配量并不等于 16% 的 CPU。要让分配优化有意义, 前提是先证明 GC 是瓶颈。

**顺带留下的一条经验**: 手写替代标准库实现时, 用旧实现做参考实现的对比测试是唯一可靠的验证方式。这次它抓到的 `$SYS/#` bug 是语义级的, 任何只测"典型用例"的测试都不会发现。

### 4.12 为什么前两次都失败: 字节占比与对象占比不是一回事

4.11 结束时留下的疑问是"38% 的 addSubscriber 该不该动"。用同一个堆剖析换一个采样维度回答它: 同一份数据, 按**对象数**而不是**字节数**排:

| 函数 | 字节占比 | 对象占比 |
|------|---------|---------|
| addSubscriber | 38.11% | **1.16%** |
| protocol.MatchTopic (strings.genSplit) | 16.19% | **30.75%** |
| doDeliver | 19.39% | 14.22% |
| protocol.writeString | 4.85% | 19.74% |
| bytes.NewBuffer | 12.44% | 15.19% |
| bufferpool.(*Pool).Put | 6.68% | 15.27% |

**`addSubscriber` 用了 38% 的字节, 却只产生 1.16% 的对象。** 它分配的是**少量大块** -- `Match` 里 `make([]Subscriber, 0, 4)` 在 200 个订阅者时扩容到 256, 六次 realloc 每次复制一个数组。字节数看着吓人, 对象数几乎可以忽略。

反过来, `genSplit` 只占 16% 的字节却是 30.75% 的对象 -- 每条消息每个订阅造两个小切片, 全是碎片。

**这两个指标回答的是不同的问题**: 对象数决定 GC 要扫描多少次, 字节数决定 GC 要标记多少内存。而**吞吐和延迟由 CPU 决定**, 两者都只是 CPU 的间接代理。这也正是 4.10 和 4.11 两次失败的共同原因:

- 4.10 看 CPU profile, `write(2)` 占 50%, 于是合并 syscall -- 但那 50% 是数据拷贝, 不是调用开销。
- 4.11 看 alloc_space, `MatchTopic` 占 16%, 于是消除它的分配 -- 但那 16% 是字节数, 不是 CPU, 换来的是更多分支。

**真正决定性的证据在 CPU profile 里**: GC 相关函数 (gcBgMarkWorker / gcDrain) 没有进入前 22 名。**分配多, 但 GC 不忙** -- 所以任何以减少分配为目标的改动, 都不会改善吞吐或延迟, 最多降低 GC 频率。这是可以提前判断的, 代价只是先看一眼 CPU profile 里有没有 GC。

### 扇出路径还能优化什么

三次测量 (CPU profile / alloc_space / alloc_objects) 加上两次失败实验, 指向一个不太受欢迎的结论:

**单机扇出的瓶颈是数据搬运本身。** 一半 CPU 在 `write(2)` 里拷贝 256 字节到内核, 这个成本无法靠"写得更聪明"消除 -- 只能靠减少要搬运的字节, 或者不让它经过用户态。

在这个代码库范围内, 剩下的方向不是微优化:

1. **减少拷贝次数**。现在一条消息从收到发出, 至少要经过: 解码拷贝 -> bufferpool -> 每个订阅者的编码写入。如果编码能直接写进 socket 的发送缓冲区而跳过中间 buffer, 省的是真实的拷贝。
2. **减少发送次数**(不是合并 syscall, 而是减少订阅者数量 x 消息数)。共享订阅、主题去重等都属此类, 属于产品能力而非内核优化。
3. **接受现状**。2 核 44.9 万投递/s、每核 18 万, 对一个 MIT 许可的单机 broker 不算差, 而继续在 5% 的量级上折腾, 风险已经大于收益。

本轮选择了第 3 条: **代码回到 `ca89cbc37`, 只保留 pprof 这个诊断能力**。两次失败的实验和它们的解释留在报告里, 因为它们比成功案例更能防止后来者重复。

## 7. 补齐计划

要能在对外材料里写性能, 还缺四组测量。按信息价值排序:

| 序号 | 测量 | 目的 | 方法 |
|------|------|------|------|
| 1 | 高 fanout 梯度 (100/200/500) | 找实时上限拐点 | **本轮已完成, 见 4.5 节** |
| 2 | 大连接数: 空闲连接 | 对标 smart-mqtt 的"10 万+ 设备" | **已完成 (4.6 节)**: loadgen 新增 `-mode idle`, 稳定支持 5,000, 35-38 KB/连接 |
| 3 | 10,000 连接为何恰好失败一半 | 判断是 Windows 限制还是 broker 缺陷 | broker 日志落盘 + Linux 复测 |
| 4 | 多发布者 fanout (8 pub / 200 sub) | 分离"单连接串行"与"broker 容量" | **已完成 (4.5 节)**: 加发布者只 +12% 吞吐, 延迟恶化 3 倍 |
| 5 | 同硬件复测 4g 的 M3 场景 | 消除 fanout 与硬件两个变量 | 需在 14C+ 机器上各跑一轮, 同 payload 同速率 |
| 6 | Linux 上的当前 HEAD 基线 | 2026-10-15 的基线落后 14 个提交 | 重复 `2026-10-15-server-baseline.md` 的方法, 确认无退化 |

其中第 1 项已完成。第 3 项只需改 `-publishers` 参数, 是下一步代价最低的测量, 而且它能回答一个关键问题: 4.5 节的拐点究竟是"单连接串行"造成的, 还是 broker 的 fanout 路径本身有上限。第 2 项需要新增 loadgen 模式; 第 4、5 项需要外部 Linux 机器 (云主机已释放)。

在完成第 2、3 项之前, 对外只应写"协议完整性"与"资源占用", 并写 fanout 100-150 的实时边界; 不应写笼统的吞吐数字。
