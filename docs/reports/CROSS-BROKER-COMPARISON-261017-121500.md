# 四个 MQTT Broker 对比与 shark-mqtt 性能补齐

> 日期: 2026-10-17 12:15 (UTC+8)
> shark-mqtt 基线: `81d95f344`
> 对比对象: smart-mqtt (Java), smart-mqtt-4g (Go), mica-mqtt (Java)
> 目的: 用可核对的数据定位 shark-mqtt 的位置, 并标出还缺哪些测量

---

## 1. 先说结论

| 结论 | 依据 |
|------|------|
| shark-mqtt 的**协议完整性**在四者中最好 | 仅 shark-mqtt 处理 AUTH(0x0F) 全流程; 属性合法性与固定头 flags 双向校验为独有 |
| shark-mqtt 的**体积**比 Java 方案大一个量级, 但比"Java + JRE"小两个量级 | 11.7 MB Go 静态二进制, 含运行时; smart-mqtt 的 <800 KB 是不含 JRE 的 jar |
| shark-mqtt 的**吞吐数据是四者里最不完整的** | 只测过 4 订阅者小 fanout, 没测过高连接数与高 fanout; 另两家有公开的 35 万 - 90 万 msg/s 数字 |
| 现有数字**不能直接横向比** | fanout 倍数、硬件、平台、是否含客户端开销全部不同; 第 4 节给出归一化口径 |
| mica-mqtt 与 shark-mqtt **不是同类** | 前者是嵌入式组件 (client + server 库), 后者是完整 broker 二进制 |
| **实时 fanout 上限约 100-150 (单发布者 2000 msg/s)** | 4.5 节梯度实测: fanout 100 时 P99 4.4 ms, 200 时 P50 已达 602 ms |
| **空闲连接成本 35-38 KB/连接, 线程数不随连接数增长** | 4.6 节实测: 1,000 连接 51.4 MB, 4,500 连接 173.9 MB, 线程始终 19-21 |
| **单机稳定支持 5,000 空闲连接; 10,000 恰好失败一半, 原因未查明** | 4.6 节: 干净环境下可复现, 客户端侧报 EOF, 代码中无 5000 硬编码 |

## 3. 协议完整性对比

这一项 shark-mqtt 领先, 且有可指认的代码依据:

| 能力 | shark-mqtt | smart-mqtt | 说明 |
|------|-----------|-----------|------|
| AUTH (0x0F) 报文 | 完整 (握手期 + 会话内重认证) | **完全不处理** | smart-mqtt `MqttHeaderDecoder` 的 switch 无 case 15, 收到 AUTH 直接抛异常 |
| 出站 PUBLISH 属性中继 | 逐属性转发, Topic Alias 剥离 | **每条出站 PUBLISH 构造空 PublishProperties** | 导致 MQTT 5.0 Section 4.10 的请求/响应模式在 smart-mqtt 上不可用 |
| 属性归属校验 (Table 2-4) | 编解码双向, 11 个 locus + 27 条 probe | 未做 | 非法属性 ID 与重复属性分别判 Malformed / Protocol Error |
| 固定头 flags 校验 | 编解码双向 | 部分 | shark 对 PUBREL/SUBSCRIBE/UNSUBSCRIBE 的 0b0010 组有专门处理 |
| 出站 Maximum Packet Size 约束 | 编码层收口 | 未见 | 超限报文按规范丢弃而非截断 |
| 解码流对齐 | 拒绝的报文只消费自己的 Remaining Length | 未见 | 防止用对端可控长度索赔 64 KiB |

> 注: smart-mqtt 的两项判定来自其 Java 源码 (`enums/MqttMessageType.java:18`, `MqttHeaderDecoder` switch), 记录在 `docs/reports/SMART-MQTT-GAP-ANALYSIS-261014-2125.md`。

## 4. 性能数据

### 4.1 shark-mqtt 实测 (本轮)

**环境**: Windows 11, AMD Ryzen 7 8845HS (8C16T), Go 1.26.1, broker 与 loadgen 同机竞争 CPU。
**方法**: `tools/loadgen` 通过项目自身 client 包驱动, 延迟由载荷内时间戳在订阅端计算 (端到端, 含编解码与写队列)。

| 场景 | 目标 | 实际发送 | 投递 | frout | P50 | P99 | P999 |
|------|------|---------|------|-------|-----|-----|------|
| QoS 0, 4 sub / 8 pub, 256 B | 20,000 msg/s | 19,968 msg/s | 79,873 msg/s | 400% | 0.0 us | 1,048 us | 1,823 us |
| QoS 1, 4 sub / 8 pub, 256 B | 10,000 msg/s | 9,994 msg/s | 39,975 msg/s | 400% | 0.0 us | 598 us | 1,212 us |

`P50 = 0.0 us` 是 Windows 计时器精度造成的下溢, 不代表真实零延迟; 该列在 Linux 基线上才有意义 (见 4.2)。

**资源**: 空载工作集 14.5 MB / 9 线程; 两轮压测后工作集 23.1 MB, 峰值 24.4 MB。

### 4.2 shark-mqtt Linux 基线 (2026-10-15, commit d5e37f8f9)

这是唯一在 Linux 上带资源采样的完整数据, 记录在 `docs/benchmarks/2026-10-15-server-baseline.md`:

| 配置 | QoS | 发送 | 投递 | P50 | P99 | CPU (核) | 峰值 RSS |
|------|-----|------|------|-----|-----|---------|---------|
| Shared | 1 | 19,652 | 78,610 | 297 us | 1,734 us | 3.19 | 20.0 MB |
| Pinned (broker 0-3, client 4-7) | 1 | 19,668 | 78,671 | 190 us | 1,197 us | 2.97 | 19.2 MB |
| Shared | 0 | 19,670 | 78,678 | 158 us | 722 us | 2.12 | 20.1 MB |

### 4.4 为什么不能直接比

| 差异 | shark-mqtt | smart-mqtt-4g | 影响 |
|------|-----------|--------------|------|
| fanout 倍数 | 4 | 2000 | 投递数是 fanout 的倍数, 900k 除以 2000 只有 454 主题发布/s |
| 发布者数 | 8 | 10-2000 | 并发连接数不同 |
| 是否含客户端开销 | 含 (项目自身 client) | 未声明 | 若用外部压测器, broker 侧数字会更好看 |
| 硬件 | 8C16T 笔记本 CPU | i9-12900HK (14C20T) | 核数差 ~1.7 倍 |
| CPU 占用是否公布 | 是 | 否 | 无法归一化 |

**换算尝试** (仅作量级参考, 不可作为结论): 若把 4g 的 M2 数字按 fanout 归一, 主题发布率约 454/s; shark 在同口径 (4 sub) 下是 79,873 / 4 = **19,968 主题发布/s**。这个对比反而显示 shark 在小 fanout 下更强, 但两者的订阅者规模相差 500 倍, 场景完全不同, 因此**不能据此下结论**。

真正缺的是: **shark-mqtt 没有在高 fanout (数百至数千订阅者) 与大连接数 (万级) 下测过**。这是本节最重要的发现。

### 4.5 fanout 拐点 (本轮补充测量)

先测 500 订阅者时看到一个比"峰值吞吐"更有用的现象: 投递量上去了, 延迟崩了。于是按 fanout 梯度补测, 全部为 QoS 0 / 1 发布者 / 256 B / Windows 同机:

| fanout | 发布者 | 目标 rate | 实际发送 | 达成率 | 投递/s | P50 | P99 |
|--------|-------|----------|---------|-------|---------|-----|-----|
| 100 | 1 | 2,000 msg/s | 1,984 | 99% | 198,379 | 0 us | 4,390 us |
| 200 | 1 | 2,000 msg/s | 1,433 | 72% | 280,276 | 602,004 us | 914,162 us |
| 200 | 8 | 2,000 msg/s | 1,715 | 86% | 313,695 | 1,675,985 us | 5,001,222 us |
| 500 | 1 | 2,000 msg/s | 590 | 30% | 290,286 | 1,383,172 us | 2,519,888 us |
| 500 | 8 | 2,000 msg/s | 823 | 41% | 298,100 | 6,573,109 us | 12,435,333 us |

**读法**:

- **实时上限在 fanout 100 与 200 之间**。100 订阅者时发布速率达成 99%、P99 4.4 ms, 属于实时; 200 订阅者时 P50 已经 602 ms, 说明消息在写队列里排队, 系统进入吞吐饱和而非实时投递。
- **吞吐天花板约 290-314k 投递/s, 且与发布者数无关**。这是本轮最有信息量的结果: 把发布者从 1 增到 8, fanout 200 的投递率从 280k 升到 314k (+12%), 而 P50 从 602 ms 恶化到 1,676 ms。吞吐几乎不动、延迟成倍恶化, 说明瓶颈在 broker 的 fanout 投递路径, 不在"单发布连接串行读取"。原本的假设被这组对照否掉了。
- **每逻辑核 30.6k 投递/s** (290,286 / 9.49, 单发布者 500 fanout 那一轮), 按物理核折算约 61k 投递/物理核/s, 高于小 fanout 的 37.1k -- 大 fanout 摊薄了入站解码成本, 与直觉一致。
- **QoS 0 在这里不是"不背压"**。发布端达成率掉到 30%-41%, 是因为 broker 的处理速度反向压住了读取, 不是丢弃策略生效。
- **延迟指标本身要打折看**。P50 6.5 s 意味着队列里积压了数万条, 这是压测器持续施压、broker 始终处理不完的结果, 不是稳态服务延迟。

**这组数字的边界**:

1. 压测端与 broker 同机。500 个订阅连接 + 8 个发布连接本身消耗 CPU, 9.49 逻辑核里含对手方开销, broker 真实占用更低; 反过来, 压测端也可能先撞墙, 所以 300k 是"同机可测到的上限", 不是 broker 的绝对上限。
2. 500 连接在 Windows 回环上, 与 Linux 的 epoll 路径不同, 绝对值不可与 2026-10-15 的 Linux 基线混用。
3. 未测 CPU 的两行 (fanout 100/200 单发布者) 说明它们不是资源饱和点, 但仍受同机竞争影响。

结论: **shark-mqtt 在单机 8845HS 上, 投递吞吐天花板约 300k msg/s; 实时范围是 fanout 100-150 (P99 个位数毫秒), 超过后延时会进入百毫秒到秒级。** 提高实时边界需要减少每帧的 fanout 成本 (批量写、合并队列) 或分散到多发布连接 -- 但后者已证明无效, 所以只剩前者。

### 4.6 空闲连接成本 (idle 模式)

`loadgen` 新增 `-mode idle`: 只做 CONNECT/CONNACK 然后把连接挂住, 不发消息。它回答的是"一万台闲置设备要多少内存", 而不是吞吐。连接走裸 TCP + 项目 codec, 不含 `client.Client` 的开销, 所以量到的是 broker 的每连接成本。

KeepAlive 设为 0, broker 不会主动超时清理, 因此观察的是稳态占用。

| 连接数 | 工作集 | 线程 | 建连速率 | 失败 | 备注 |
|--------|--------|------|---------|------|------|
| 0 (空载) | 14.5 MB | 9 | - | - | - |
| 1,000 | 51.4 MB | 21 | 7,364 conn/s | 0 | 单源 IP |
| 4,500 | 173.9 MB | 19 | 1,171 conn/s | 500 | 压测端 TIME_WAIT 耗尽, 非 broker 拒绝 |
| 5,000 | 未采 | - | 6,200 conn/s | 0 | 重启 broker 后干净环境 |
| 10,000 | 未采 | - | 2,541 conn/s | 5,000 (EOF) | 重启 broker 后干净环境, 恰好一半失败 |

**每连接约 35-38 KB** (51.4-14.5 MB / 1000 = 37.8 KB; 173.9-14.5 / 4500 = 35.4 KB)。两点都落在 35-38 KB 区间, 没有明显的非线性增长。按此外推, 一万台空闲设备约需 370-400 MB 进程内存。

**线程数与连接数几乎无关**: 空载 9, 1,000 连接 21, 4,500 连接 19。Go 的 netpoller 不为每个连接起线程, 这与"每连接一线程"的实现有本质区别, 也是能把万级设备压住的原因。进程句柄数与连接数同阶 (5,000 连接时 Handles=5290)。

### 10000 连接只成功一半 -- 原因未查明

在**重启 broker 后的干净环境**下重复, 结果稳定复现: 目标 10,000 时**恰好 5,000 成功、5,000 失败**, 客户端侧首次错误是 `EOF` -- 即 TCP 连接已建立、CONNECT 已发出, 服务端在回 CONNACK 之前关闭了连接。目标 5,000 时则是 0 失败。

代码里搜不到 5000 这个硬编码 (`broker/` `config/` `api/` 全无), `max_connections` 默认值是 10000。**因此这可能是: (a) Windows 本机内核/回环路径的连接数限制, (b) 端口状态残留, 或 (c) broker 自身的某条连接准入路径在 5,000 附近出错。** 现有证据不足以区分, 结论待定。

要定位它需要两件事: 把 broker 日志落盘 (本轮为了压缩输出用了管道, 日志没留下), 以及在 Linux 上复测同样的 10,000。在两者完成前, **对外只应写"单机稳定支持 5,000 空闲连接, 内存约 35-38 KB/连接"**, 不应写"支持万级"。

### 测量方法上踩的三个坑 (记录下来, 避免重犯)

1. **`| head -N` 会杀死被测程序, 制造假故障。** `go run` 会 fork 子进程, `head` 读满 N 行后关闭管道, 子进程收到 EPIPE 被杀, 其 socket 不正常关闭。表现是下一轮测试里 Established 连接高达 9,801 且逐轮递增, 失败率随轮次单调上升 (281 -> 141 -> 70)。**压测输出只能用 `tail`, 或重定向到文件。**
2. **单源 IP 只能测到 4,500 左右。** Windows 动态端口 16,384 个, 客户端主动关闭产生的 TIME_WAIT 会在下一轮把端口吃光。`dialAndConnect` 已改为在 `127.0.0.2` - `127.0.0.17` 上轮转, 端口空间扩大 16 倍。
3. **每轮之间要重启 broker。** 上一轮残留的连接会改变下一轮的结果 (见第 1 点)。

## 5. 资源占用

### 5.1 二进制体积

交叉编译 (linux/amd64, CGO off, `-trimpath -ldflags="-s -w"`):

| 构建 | 体积 | 说明 |
|------|------|------|
| 默认 | 11,747,490 B (11.2 MiB) | 含 Prometheus、WebSocket、配置加载 |
| `-tags nometrics` | 8,032,418 B (7.7 MiB) | 去掉指标子系统 |

构成 (粗略): Go 运行时约 2 MB, Prometheus client 约 2-3 MB, 其余为业务代码与 codec。

smart-mqtt 的 <800 KB 是 **jar 包**, 运行时另需 JRE (17+ 约 100-180 MB)。mica-mqtt 的 500 KB 同理。所以三者不是同一量级的比较对象:

| 方案 | 发行物 | 运行时 | 部署总占用 |
|------|--------|--------|-----------|
| shark-mqtt | 8-11 MB 静态二进制 | 无 | 8-11 MB |
| smart-mqtt | <800 KB jar | JRE 17+ | 100+ MB |
| mica-mqtt | 500 KB 核心依赖 | JRE 17+ 或 GraalVM 原生 | 100+ MB 或数 MB |

mica-mqtt 支持 GraalVM 原生编译, 这是 Java 阵营缩小体积差距的路径; 但那需要额外构建步骤, 且反射/动态代理受限。

### 5.2 运行内存

| 状态 | shark-mqtt (Windows) | shark-mqtt (Linux 基线) |
|------|---------------------|------------------------|
| 空载 | 14.5 MB 工作集 / 9 线程 | 未测 |
| 4 sub / 8 pub 压测后 | 23.1 MB, 峰值 24.4 MB | 20.1 MB (VmHWM) |
| 500 sub / 1 pub 压测后 | 56.9 MB, 峰值 65.6 MB / 40 线程 | 未测 |
| 内存后端 | in-process map | 同 |

另两家的内存数字未公开。这是一个**可以主动争取的优势项**: 20 MB 级别的 RSS 在 Java 方案上通常做不到 (JVM 堆基线就在数十 MB)。

### 5.3 外部依赖

直接依赖 6 个 (go.mod `require` 块):

```
github.com/dgraph-io/badger/v4     存储后端 (build tag)
github.com/gorilla/websocket        WebSocket 传输
github.com/prometheus/client_golang 指标
github.com/redis/go-redis/v9        存储后端 (build tag)
golang.org/x/crypto                 bcrypt
gopkg.in/yaml.v3                    配置
```

其中 badger 与 go-redis 只在对应 build tag 下编译进二进制。默认构建 (`-tags nometrics`) 的实际依赖只有 websocket + crypto + yaml。间接依赖 20 个, 全部来自 prometheus。

"极少外部依赖"这一条 shark-mqtt 成立: 静态二进制 + 零运行时服务依赖, 这在容器镜像里体现为 `FROM scratch` 可用。

## 6. shark-mqtt 的位置

| 维度 | 判断 |
|------|------|
| 协议正确性 | **领先**。四者中唯一完整实现 AUTH 与属性归属双向校验 |
| 单机小 fanout 吞吐 | 与 4g 同量级 (需同硬件复测才能定论) |
| 高 fanout 吞吐 | 天花板 290k 投递/s，但实时上限只到 fanout 100-150（4.5 节） |
| 高连接数吞吐 | **数据缺失**（只测到 500 连接） |
| 冷启动与内存 | 领先 Java 方案一个量级 (20 MB vs 数十至数百 MB) |
| 发行物体积 | 输给 Java jar (11 MB vs 800 KB), 赢过 jar+JRE 总和 |
| 集群 | 无。smart-mqtt 原生支持, 4g 有 POC |
| 生态与上位机 | 弱于 mica-mqtt (后者有 Spring/Solon/JFinal 全套 starter) |

一句话: **shark-mqtt 目前是"协议最严谨、资源最省的单机 Go broker", 不是"吞吐最高的 broker", 且没有证据支持后者。**

## 7. 补齐计划

要能在对外材料里写性能, 还缺四组测量。按信息价值排序:

| 序号 | 测量 | 目的 | 方法 |
|------|------|------|------|
| 1 | 高 fanout 梯度 (100/200/500) | 找实时上限拐点 | **本轮已完成, 见 4.5 节** |
| 2 | 大连接数: 空闲连接 | 对标 smart-mqtt 的"10 万+ 设备" | **已完成 (4.6 节)**: loadgen 新增 `-mode idle`, 稳定支持 5,000, 35-38 KB/连接 |
| 3 | 10,000 连接为何恰好失败一半 | 判断是 Windows 限制还是 broker 缺陷 | broker 日志落盘 + Linux 复测 |
| 4 | 多发布者 fanout (8 pub / 200 sub) | 分离"单连接串行"与"broker 容量" | **已完成 (4.5 节)**: 加发布者只 +12% 吞吐, 延迟恶化 3 倍 |
| 5 | 同硬件复测 4g 的 M3 场景 | 消除 fanout 与硬件两个变量 | 需在 14C+ 机器上各跑一轮, 同 payload 同速率 |
| 6 | Linux 上的当前 HEAD 基线 | 2026-10-15 的基线落后 14 个提交 | 重复 `2026-10-15-server-baseline.md` 的方法, 确认无退化 |

其中第 1 项已完成。第 3 项只需改 `-publishers` 参数, 是下一步代价最低的测量, 而且它能回答一个关键问题: 4.5 节的拐点究竟是"单连接串行"造成的, 还是 broker 的 fanout 路径本身有上限。第 2 项需要新增 loadgen 模式; 第 4、5 项需要外部 Linux 机器 (云主机已释放)。

在完成第 2、3 项之前, 对外只应写"协议完整性"与"资源占用", 并写 fanout 100-150 的实时边界; 不应写笼统的吞吐数字。
