### 修复前的 5000 上限

本节此前的版本记录的是「5000 成功、其余失败」, 并把原因归给压测客户端。**那是错的**: 真实原因是 broker 的 `pendingConns` 在注册时未消耗, 每个连接被双计, 实际上限恒为 `maxConnections` 的一半, 且残留计数断开后不回收。修复后默认配置 (10000) 下以上三档全部零失败。详见 [CROSS-BROKER-COMPARISON](../reports/CROSS-BROKER-COMPARISON-261017-121500.md) 4.6 节。

loadgen commit `25e88247b`。

| 项 | 值 |
|----|----|
| 时长 | 600 s |
| 发送 | 11,999,992 |
| 投递 | 47,999,992 |
| 投递率 | 400.00% |
| 错误 | **0** |
| 投递/s | 79,177 |
| P50 / P99 / P999 | 187 / 681 / 2,113 us |
| broker RSS 起始 / 峰值 / 结束 | 16.3 / 16.8 / 16.7 MB |
| broker 线程 | 9 (全程不变) |
| broker CPU | 0.688 核 (41,275 ticks / 600 s) |

**RSS 在 10 分钟内持平, 没有单调爬升**: 21 个采样点 (30 s 间隔) 全部落在 16.3-16.8 MB 区间, 首尾差 0.4 MB, 属于 GC 锯齿而非泄漏。线程数 9 从头到尾没变。

**混合负载比纯 QoS 0 贵**: 同样 4 订阅者 8 发布者, 纯 QoS 0 用 0.43 核, 70/30 混合用 0.688 核 (+60%), P99 从 505 us 升到 681 us。30% 的 QoS 1 消息要付 PUBACK 往返与 inflight 记账。

录到的 `rss_timeline` 有 20 个点; broker 侧的独立采样 (`/root/soak_rss.txt`) 有 21 个点 -- 跨机时 `-pid` 采不到对端进程, 这是两个独立循环, 时间戳只能对齐到 30 秒粒度。

## H. 混合 payload (QoS 0, rate 20,000, 4 订阅者 / 8 发布者, 跨机)

模拟设备群同时上报心跳与大块遥测: 80% 的 64 B 加 20% 的 4 KB, 平均 870 B。

| 场景 | 发送 | 投递/s | P50 | P99 | P999 |
|------|------|--------|-----|-----|------|
| 纯 64 B | 19,802 | 79,207 | 187.7 us | 564.3 us | 2,049 us |
| 纯 4 KB (rate 5,000) | 4,987 | 19,949 | 162.5 us | 401.8 us | 2,109 us |
| **混合 80/20** | 19,800 | **79,200** | 185.1 us | **692.4 us** | 2,106 us |

**混合负载的投递率与纯小包一致**: 79,200 对 79,207。20% 的 4 KB 帧没有拉低消息处理速率, 因为这一档的字节速率 (79,200 x 870 B = 69 MB/s, 约 550 Mbps) 离 2.9 Gbps 的链路天花板还很远。

**代价体现在延迟尾部**: P99 从 564 us 升到 692 us (+23%), P999 基本不动。也就是说大帧影响的是尾部而非中位数 -- 与"每帧固定开销主导"的结论一致: 大帧只是偶尔让某一帧变贵。

## I. 混合场景: 万级在线 + 小规模流量 (最接近真实部署)

前面的测试把"连接数"和"吞吐"分开测。真实设备群是两者叠加: 一万台设备在线, 其中少量在发
消息、更少量在收。`loadgen -online N` 用来表达这个形状 -- N 个连上但不订阅的连接。

配置: `-online 9890 -subscribers 10 -publishers 100`, 合计 **10,000 个连接**, QoS 0, 256 B, 跨机 25 s。

| 项 | 值 |
|----|----|
| 连接 | 10,000 (9,890 静默 + 10 订阅 + 100 发布) |
| 发送 | 19,384 msg/s |
| 投递 | 193,838 msg/s (1000% = 10 订阅者) |
| 错误 | **0** |
| P50 / P99 / P999 | 1,122 / 4,043 / 8,290 us |
| broker VmHWM | **423 MB** |
| broker 线程 | 8 |
| broker CPU | **0.82 核** (23.72 s / 29 s 墙钟, 共 2 核) |

**一万连接 + 近 20 万投递/秒, 只用 0.82 核。** 2 核机器还有一半余量, 内存 423 MB 对 4 GB 也很宽松。

**延迟比小规模差一个量级**: 同样是 QoS 0 / 256 B, 4 订阅者 8 发布者时 P50 是 182 us, 这里
是 1,122 us。原因是单个订阅者的接收压力变了 -- 10 个订阅者分摊 193,838 投递/秒, 每个要收
约 19,400 msg/s, 而前面的测试里每个订阅者只收 19,800 msg/s 的四分之一。

**内存比纯空闲多 165 MB**: 纯 10,000 空闲连接是 258 MB, 混合场景 423 MB。差额来自 110 个
活跃连接的写队列、inflight 记账与消息缓冲, 静默连接本身几乎不增长。

## J. 30 分钟长稳 (混合负载, 3.6 亿条消息)

修复延迟采样上限之后, 30 分钟长稳第一次跑完。参数: `-online 2000 -subscribers 10 -publishers 100`,
QoS 70/30, payload 64/1024 按 80/20, rate 20,000, 跨机。

| 项 | 值 |
|----|----|
| 时长 | 1,801 s (30 分钟) |
| 发送 | 35,999,888 |
| 投递 | **359,998,900** (3.6 亿) |
| 错误 | **0** |
| 投递/s | 199,922 |
| P50 / P90 / P99 / P999 | 649 / 2,325 / 7,500 / 12,141 us |
| broker RSS 起始 -> 结束 | **109.8 -> 112.0 MB** (+2.2 MB, +2%) |
| broker 线程 | 9 (全程不变) |
| broker CPU | 1.36 / 2 核 |

**broker 侧**: 65 个采样点 (30 s 间隔), RSS 从 109,796 kB 走到 111,964 kB, **半小时只涨 2.2 MB**,
线程数从头到尾是 9。同期 3.6 亿条消息和 0 错误。**没有泄漏迹象**。

**压测侧**: loadgen 的 RSS 恒定在 91 MB (修复前的同一参数在 11 分钟就被 OOM 杀掉, 见 4.12
节的下一条)。延迟样本达到 500,000/订阅者的上限, JSON 里 `latency_capped: true` 明示 --
分位数来自前 26 秒的 500 万样本, 之后的投递只计数不再采样。

**这组数据的意义在于时间跨度**: 之前的 10 分钟长稳只能说"没有快速泄漏", 30 分钟、3.6 亿条
消息、RSS 增幅 2%, 才足以支持"稳态无泄漏"这个说法。
